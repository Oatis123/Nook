# Decisions

One line per decision left to the agent's discretion by TECH_SPEC.md, in the format:
`YYYY-MM-DD — decision — reason`.

- 2026-09-17 — Working name "Nook" is exposed as a single `APP_NAME` env var (see `.env.example`), read by frontend/backend/bot so it can be renamed without code changes — spec §0 requires this.
- 2026-09-17 — Python tooling: `uv` for dependency management, `ruff` for lint/format, `mypy` for types — faster and simpler than Poetry, single static binary, current ecosystem default.
- 2026-09-17 — Frontend package manager: `pnpm` — fast, disk-efficient installs, standard for modern Vite/TS projects.
- 2026-09-17 — Global/local note graph rendered with `react-force-graph-2d` (wraps d3-force + canvas) instead of a hand-rolled d3-force/canvas renderer or sigma.js — production-proven canvas performance at 2000+ nodes without spending implementation time on a custom renderer.
- 2026-09-17 — Calendar view is a custom implementation on top of `date-fns` rather than FullCalendar — spec prefers this explicitly; avoids fighting FullCalendar's CSS to match the design system.
- 2026-09-17 — Full-text search: `notes` gets two generated `tsvector` columns (`search_vector_en` using the `english` config, `search_vector_ru` using `russian`), queried with OR; a `pg_trgm` GIN index on `notes.title` powers fuzzy quick-switcher matching — correct stemming for both languages without extra services.
- 2026-09-17 — Fonts (all self-hosted via `@fontsource`, no Google Fonts CDN): headings/note titles — Literata (serif); interface — IBM Plex Sans (humanist sans); editor/code — JetBrains Mono.
- 2026-09-17 — Reminder delivery worker is a plain asyncio loop (30s tick, `SELECT ... FOR UPDATE SKIP LOCKED`) with no Redis/Celery — spec §8.4 mandates this explicitly.
- 2026-09-17 — Recurrence stored as an RFC 5545 RRULE string (`python-dateutil.rrule` for expansion) plus `dtstart_local` and the user's IANA timezone, per spec §7.4/§11.
- 2026-09-17 — The no-flash theme bootstrap script is a same-origin external file (`public/theme-init.js`, classic non-module `<script src>`) rather than an inline `<script>` — lets nginx's CSP use `script-src 'self'` with no `'unsafe-inline'`/nonce exception while still running synchronously before first paint.
- 2026-09-17 — nginx CSP (`deploy/nginx.conf.template`) allows `style-src 'unsafe-inline'` only — Radix UI primitives set inline `style` for computed popover/tooltip/menu positioning, which can't be pre-hashed; `script-src` stays `'self'` with no exception. Inline style injection is a much smaller attack surface than inline script.
- 2026-09-17 — Login rate limiting (spec §5.4: 5 attempts / 15 min per username+IP) is an in-process sliding-window counter (`app/core/rate_limit.py`), not a DB table or Redis — consistent with the no-Redis/Celery constraint (§8.4) and the single-API-process deployment; resets on restart, which is an acceptable trade-off for a self-host brute-force guard.
- 2026-09-17 — Opaque tokens (invites, auth_tokens, refresh_tokens) are generated with `secrets.token_urlsafe(32)` and stored hashed with SHA-256 (`app/core/tokens.py`), not argon2 — they're high-entropy random tokens, not user-chosen passwords, so there's no brute-force risk to slow down against, and SHA-256 avoids needless per-request hashing cost.
- 2026-09-17 — Access tokens are JWTs (HS256, `app/core/jwt.py`) signed with `SECRET_KEY`; refresh tokens are opaque random tokens stored hashed in `refresh_tokens`, matching spec §5.4 ("refresh token... хранится в БД в хешированном виде").
- 2026-09-17 — The test suite runs against a separate `<POSTGRES_DB>_test` database (auto-created by an autouse fixture in `backend/tests/conftest.py`), never the one used by `docker compose up` / manual runs — `db_engine`'s per-test `create_all`/`drop_all` would otherwise wipe real dev/prod data if pointed at the same database.
- 2026-09-17 — All date/time display goes through `frontend/src/lib/format.ts`, which pins `'en-US'` explicitly. Found via live browser testing: `toLocaleDateString(undefined, ...)` uses the browser's OS locale, which rendered Russian month names on this dev machine — spec §0 requires an English-only interface regardless of the visitor's browser/OS locale. Every later stage (tasks, calendar, reminders) must use these helpers instead of calling `toLocale*` directly.
- 2026-09-17 — Deleting a folder soft-deletes it and cascades to every descendant folder and every note inside any of them (same `deleted_at` timestamp), rather than requiring an empty folder or hard-deleting contents. Spec §11 gives folders their own `deleted_at`, implying trash semantics; only notes are ever shown in the Trash UI (folders aren't independently restorable — restoring a note whose folder was deleted just drops it to root instead of resurrecting the folder tree).
- 2026-09-17 — "Note title unique within a folder" (§6.1) is enforced with an application-level check (query before insert/rename), not a partial unique DB index — simpler, and race conditions are a non-issue at this app's single-user-editing scale.
- 2026-09-17 — The 30-day trash auto-purge (§6.1) is lazy: `purge_old_trash()` runs at the start of every note-list call rather than via a dedicated scheduled job, keeping the worker limited to reminder delivery (§8.4's explicit scope).
- 2026-09-17 — Shiki (code highlighting in the note preview) is wired via its "fine-grained bundle" API (`shiki/core` + `shiki/engine/oniguruma` + per-language `shiki/langs/*` dynamic imports in `frontend/src/features/notes/shiki.ts`), not the convenience `shiki`/`@shikijs/rehype` default export — the convenience API eagerly bundles its full ~200-grammar catalog. A curated language subset keeps each grammar in its own lazy chunk. Route-level code splitting (lazy-loading NoteEditor/AdminPage/etc.) and further bundle-size work is left for the Stage 14 polish pass rather than perfected now.
- 2026-09-17 — Wikilink `folder/Title` resolution matches the note's immediate containing folder's *name* only, not a full nested path — a one-level approximation of a full path (agent's discretion, `resolve_target` in note_links.py), since spec §6.5 doesn't fully specify the algorithm and most vaults won't have same-named notes in same-named folders at different depths.
- 2026-09-17 — Found via live browser testing: the sidebar's "New note" button always requested the literal title "Untitled", which 409-conflicted (silently, no UI feedback) once one already existed in that folder — clicking it did nothing visible, and if the user then typed assuming a blank editor, the keystrokes landed in whatever note was still open, corrupting it. Fixed with `uniqueNoteTitle()` (frontend/src/features/notes/tree.ts), which appends " 2", " 3", ... against the already-fetched notes list before creating. Not a backend bug — general lesson: any default-named "create" action needs collision-avoidance up front, not error handling after the fact.
- 2026-09-17 — Docker Desktop was installed/started partway through Stage 2. From then on, backend tests run against the real `db` service (`docker compose up -d db`, with a gitignored `docker-compose.override.yml` publishing 5432 to the host for local `pytest`/`alembic` runs outside Docker) instead of being limited to lint/type-check/collect-only.
- 2026-09-17 — Found via a full `docker compose up --build` (first run of the complete stack, in Stage 6): `deploy/nginx.conf.template`'s `location /api/ { proxy_pass http://api:8000/; }` had a trailing slash on the proxy target, which makes nginx strip the `/api/` location prefix before forwarding — so `/api/v1/auth/login` reached the backend as `/v1/auth/login`, matching no route (404) despite the same request working fine through Vite's dev proxy (which forwards the path unchanged). Fixed by dropping the trailing slash (`proxy_pass http://api:8000;`), which passes the original URI through as-is, matching `APIRouter(prefix="/api/v1")`. This had been present since Stage 1 and undetected because the full stack hadn't been built end-to-end before now — general lesson: `docker compose up` for the *whole* stack (not just `db`) needs to actually run at least once before a stage is called done, since dev-server proxying and the production nginx config are two independent code paths that can silently diverge.
- 2026-09-17 — Found via the Stage 6 production build (`tsc -b && vite build`, run inside the `web` Docker image): a plain `npx tsc --noEmit` at the repo root passed cleanly but missed a real type error that the project's actual `pnpm run typecheck` (`tsc -b --noEmit`, using the composite `tsconfig.app.json`/`tsconfig.node.json` project references) caught — importing React's `KeyboardEvent` type under the same name as the DOM's global `KeyboardEvent` silently shadowed the global for a `window.addEventListener('keydown', ...)` call elsewhere in the same file. Fixed by aliasing the React import (`type KeyboardEvent as ReactKeyboardEvent`). General lesson: verify frontend types with the project's own `typecheck`/`build` script, not a bare `tsc --noEmit`, since they can disagree.
- 2026-09-17 — Found in the same full-stack run: the `web` service's healthcheck (`wget -qO- http://localhost:80`) reported "unhealthy" even though the app was serving requests correctly — this `nginx:alpine`-based image's musl libc resolves `localhost` to `::1` first, but nginx only binds `0.0.0.0:80` (IPv4), so `wget` got "connection refused" over IPv6 and never fell back to IPv4. Fixed by pointing the healthcheck at `http://127.0.0.1:80` explicitly. The `api` service's own healthcheck was unaffected since its Debian-based Python image's libc resolves `localhost` to IPv4 first.
- 2026-09-17 — Stage 7 graph: `GET /api/v1/graph` is one endpoint with two modes — global (default; folder/tag/hide_orphans/show_dangling filters, `app/services/graph.py:build_global_graph`) and local (`note_id`+`depth` params switch to `build_local_graph`, an undirected BFS from that note). Local graph intentionally ignores the folder/tag/hide_orphans filters — the spec only describes those for the global view, and "orphan" is meaningless for a BFS neighborhood that's non-empty by construction.
- 2026-09-17 — A node's `link_count` (drives both node size and the "hide orphans" cutoff) is the degree within the edges actually returned in that response — i.e. relative to the current filters/local-graph scope, not the note's total connectivity — since that's what the size on screen should represent to the viewer, and it keeps `hide_orphans` self-consistent (an "orphan" is anything with zero visible edges, not zero edges globally).
- 2026-09-17 — Dangling wikilinks in the graph get a synthetic node id `dangling:<target_raw>` (not a real note id) so they can be filtered (`show_dangling`), sized, and clicked like any other node; clicking one creates a note with that title and navigates to it, reusing the same create-on-click behavior the note preview's dangling wikilinks already have (spec §6.5).
- 2026-09-17 — The graph's "show tasks as nodes" filter (spec §6.6) is deferred until Stage 10 (task↔note links) since tasks don't exist yet — same reasoning as `in:tasks` in Stage 6's search. Not built as a dead/disabled toggle in the meantime; it'll be added alongside the task-node data when it exists.
- 2026-09-17 — `react-force-graph-2d` (chosen in Stage 1 for the graph view) auto-detects its canvas width from the nearest ancestor with a definite CSS width. Found via live testing: inside the narrow local-graph panel (a flex/aside column), that auto-detection picked up a distant, much wider ancestor instead, rendering an oversized canvas that silently overflowed the panel and never appeared on screen (the exact same code looked fine on the full-width global graph page only because the correct and mis-detected widths happened to coincide there). Fixed by having `GraphCanvas` measure its own wrapper `div` with a `ResizeObserver` (`frontend/src/lib/useElementSize.ts`) and pass that width to `ForceGraph2D` explicitly, rather than relying on the library's auto-detection in either context.
- 2026-09-17 — `GraphCanvas` renders with `autoPauseRedraw={false}` (continuous per-frame repaint) rather than the library's default of pausing once the force simulation settles — hover-driven neighbor highlighting and link dimming are read from a ref inside the canvas paint callbacks each frame (not React state), so they need the render loop to keep running to ever show up; the trade-off is a small constant CPU cost for a always-live canvas instead of one that goes idle, judged acceptable for an interactive graph view.
- 2026-09-17 — Node color (by folder or tag, spec §6.6) uses a deterministic string→HSL hash (`frontend/src/features/graph/colors.ts`) rather than a fixed palette keyed to folder/tag ids — works for an unbounded number of folders/tags with no palette-exhaustion or lookup-table maintenance, at the cost of occasional close hue collisions between unrelated folders/tags, which was judged an acceptable trade for this view's purpose (visually grouping, not precise categorical legends).
- 2026-09-18 — Stage 8 tasks: the `tasks` table is created with its full spec §12 column set now — including `is_recurring`/`rrule`/`dtstart_local`/`recurrence_end` — rather than ALTERing it again in Stage 9, since the spec lists them as one entity's shape. Only the non-recurring columns are settable through Stage 8's API/schemas; recurrence creation, expansion, `task_completions`, and quick-add/bot "every ..." parsing land in Stage 9 alongside the rest of the recurring-task machinery they depend on — matching the roadmap's own stage split (§14: "8. Tasks core" vs "9. Recurring tasks + Calendar") and the same precedent as Stage 6 deferring `in:tasks` search.
- 2026-09-18 — Subtasks are exactly one level deep (spec §7.3): `create_task` rejects a `parent_id` that itself already has a parent (400), and a subtask always inherits its parent's `list_id` (a `list_id` passed alongside `parent_id` is ignored) rather than allowing subtasks to live in a different list than their parent — subtasks are always viewed/managed nested under their parent, never independently filtered by list.
- 2026-09-18 — Completing a task with open subtasks doesn't silently force-complete them: `POST /tasks/{id}/complete` 409s unless `complete_subtasks: true` is sent, and the frontend shows a confirm dialog on that 409 (`CompleteSubtasksDialog`) — matches spec §7.3's "dialog: complete all / cancel" requirement directly instead of guessing intent.
- 2026-09-18 — Task deletion is a soft-delete (`deleted_at`, cascading to subtasks) matching the `tasks.deleted_at` column in the spec's data model, but there's no dedicated Trash/restore UI for tasks — unlike notes (spec §6.1), the spec never describes task trash/restore behavior, only that the column exists (useful so completions/reminders logic can simply filter deleted tasks out). Revisit if a later section turns out to need it.
- 2026-09-18 — Today/Upcoming views only surface top-level tasks (`parent_id IS NULL`); a subtask's own due date, if any, is visible only inside its parent's detail view. Keeps "what's due" aggregation consistent with the List view's own top-level-only listing, and avoids double-counting a subtask both under its parent and standalone in Today/Upcoming.
- 2026-09-18 — "Today"/"Upcoming" filtering computes "today" server-side from `user.timezone` (spec §8.1), but the client-side Overdue/Today and per-day bucketing (splitting that already-filtered set into visual groups) uses the browser's local date. These only disagree when the browser's timezone differs from the user's configured profile timezone, in which case a task could land in the wrong visual bucket (never the wrong view) — accepted as a narrow edge case; Stage 9's calendar view should reuse whichever approach it needs consistently.
- 2026-09-18 — List view's "sort" (spec §7.6) is folded into the group-by choice (Date/Priority/No grouping) rather than a separate independent sort control — each grouping mode has a sensible built-in task order (by priority-then-date within a group), which covers the practical need without a second control most users wouldn't reach for independently.
- 2026-09-18 — Quick add (spec §7.7) shows what it parsed as a row of chips below the input (date/time, priority, list) instead of highlighting the recognized substrings inline within the text field itself — true in-text highlighting in a plain `<input>` needs a contenteditable/overlay technique disproportionate to the value here; the chip row conveys the same "see what will be created before confirming" information the spec asks for.
- 2026-09-18 — An unmatched `#tag` in quick add (no task list with that name) is left as literal text in the created task's title rather than silently dropped or auto-creating a new list — avoids silent data loss; the list-name candidate is still shown as a chip only when it resolves to a real list.
- 2026-09-18 — List colors/icons come from fixed, curated sets (spec §7.2/§10.3: "ограниченной палитры") — six `--palette-N` design tokens and sixteen Lucide icon keys — validated as Postgres enums server-side (`TaskListColor`/`TaskListIcon`) and mirrored as TS union types client-side, not a free color/icon picker.
- 2026-09-18 — Stage 9 recurrence: spec §7.4's preset list (daily; weekly on chosen days; monthly by day-of-month or last day; yearly; every N days/weeks/months; "custom") has no separate "custom" code path — every preset reduces to `freq` + `interval` + `by_weekday`/`by_month_day`, so `RecurrenceInput` (`app/services/recurrence.py`) covers all of them with one structured shape; the backend builds the canonical RFC5545 string from it (`build_rrule`) rather than trusting a client-supplied RRULE string directly.
- 2026-09-18 — `recurrence_end` (spec's data model) is a cached, precomputed value — the date of the rule's actual last occurrence (via `dateutil.rrule` expansion at creation/edit time), not a raw pass-through of the RRULE's own `UNTIL`/`COUNT` clause — so "does this recurrence still have future occurrences" never needs to re-parse/expand the rule just to answer that.
- 2026-09-18 — `task_completions.completed_at` doubles as the timestamp for *both* a real completion and a skip (`skipped=true`) — the table has no separate "skipped_at" column, and the row's `skipped` flag already distinguishes which action happened; reusing the one timestamp column for whichever action fired avoids adding a column the spec's data model doesn't list.
- 2026-09-18 — Completing or skipping a recurring task's current occurrence never resets or touches its subtasks — the spec doesn't describe how subtasks interact with recurrence, and subtasks already completed under a previous occurrence simply stay completed when the parent advances. Worth revisiting if a later stage's testing surfaces a real need for per-occurrence subtask resets.
- 2026-09-18 — The calendar endpoint (`GET /tasks/calendar`) shows both open and done tasks in range, unlike List/Today/Upcoming's open-by-default — a calendar is a "what happened/happens on this day" view, so a completed task should still show (crossed out) on the day it was due, the same way a plain non-recurring completed task would.
- 2026-09-18 — Virtual occurrence expansion for the calendar is bounded to start from a recurring task's *current* (still-pending) occurrence onward, never earlier — `dateutil.rrule` would otherwise happily re-derive every occurrence since `dtstart`, including ones already resolved into `task_completions` history, which would wrongly resurrect them as "virtual" entries when browsing a past date range.
- 2026-09-18 — The Repeat picker (`RecurrencePicker.tsx`) always opens with a fresh default draft rather than reverse-parsing the task's existing RRULE string back into structured fields — the API only returns the raw string (spec's own storage format), and round-tripping it back into freq/interval/weekday/end-condition inputs just to prefill a form the user is about to overwrite isn't worth the parser it'd take; the current rule's plain-English summary (`describeRrule`) is shown on the button itself instead.
- 2026-09-18 — Calendar drag-and-drop only changes a task's *date*, not its time — the week view lists each day's timed tasks as a simple chronological list rather than a pixel-positioned hour grid, so there's no natural "drop at 2:15pm" gesture; changing the time goes through the task detail dialog's time picker instead. Full hour-grid dragging wasn't specified precisely enough to justify the added complexity now.
- 2026-09-18 — Mobile-specific calendar layouts ("неделя/агенда" on small screens) are explicitly Stage 14 work per the spec's own roadmap (§14: "responsive... calendar→неделя/агенда"), so Stage 9 built month+week for desktop only and left mobile-specific agenda polish for that later stage rather than duplicating it now.
- 2026-09-18 — Quick add's "every ..." phrase parser (`recurrencePhrase.ts`) covers `every N <unit>`, `every <weekday list>`, `every weekday` (Mon-Fri), bare `every day/week/month/year`, and `daily`/`weekly`/`monthly`/`yearly`/`annually` — the common English phrasings a spec example ("every monday 9am") and typical todo-app quick-add conventions cover. Anything needing an end condition or monthly day-of-month goes through the task's Repeat picker instead; quick add was never meant to express the full RRULE surface.
- 2026-09-18 — Stage 10 `task_note_links` has no `user_id` column (matches the spec's data model exactly: `task_note_links(task_id, note_id)`), so every service function re-verifies ownership of *both* the task and the note via `get_owned_or_404` before touching a link — a bare id pair is never trusted, since the join table itself carries no isolation boundary to check against.
- 2026-09-18 — `services/task_note_links.py` needs `services/tasks.py.create_task` (for "New task from this note"), which rules out `tasks.py` importing back from `task_note_links.py` at module level. Resolved asymmetrically: `linked_tasks` is composed directly inside `services/notes.py`'s `build_note_detail` (safe direction, no cycle), while `linked_notes` for a task is composed at the API layer in `api/v1/tasks.py` instead of inside `services/tasks.py`'s `get_task_detail`.
- 2026-09-18 — The task-side "Linked notes" add-UI (spec §9: "добавить через поиск") is a client-side fuzzy filter over the already-fetched `useNotes()` list (same `fuzzyFilter` helper the command palette uses), not a call to the FTS search endpoint — note counts at this UI's scale (a single user's notes) don't need server-side search, and it keeps the interaction instant with no debounce/loading state.
- 2026-09-18 — The note-side "Linked tasks" panel only supports unlinking implicitly (deleting the task) and creating a *new* linked task, not linking an already-existing task to a note — the spec's own wording for this panel (§9: "кнопка New task from this note") only describes creation, unlike the task side's explicit "add through search"; linking an existing task to a note is still possible from that task's own dialog.
- 2026-09-18 — Skipped the optional (spec §9: "Желательно") "Create task from selection" editor context-menu item for Stage 10 — marked explicitly nice-to-have in the spec, and the same outcome (a task linked to the note) is already reachable via the "New task from this note" panel button.
- 2026-09-18 — Stage 11 reminders: `scheduled_reminders`'s unique `(task_id, occurrence_at, kind)` index spans every status, not just `pending` — Postgres doesn't distinguish "cancelled" from "still occupies this identity" for a plain unique index. `recompute_reminders_for_task` therefore looks up *any* existing row for a desired key (any status) and only inserts a fresh row when none exists; a `cancelled` row for that exact key is revived back to `pending` (never delivered, so safe to reuse), while a `sent`/`failed` row is left alone rather than resurrected — toggling `reminders_enabled` off then on for the same occurrence is the case this fixes (caught by a failing test during Stage 11 itself).
- 2026-09-18 — "до 3 повторов" (spec §8.4) is read as 3 attempts total, not 3 retries after an initial try (4 attempts) — `MAX_ATTEMPTS = 3` in `app/services/reminders.py`, matching the `attempts` column's own name. Backoff delays are a fixed `[1, 2, 4]` minutes schedule rather than a formula, since the spec only asks for "exponential" without specifying a base.
- 2026-09-18 — A reminder that can't be delivered because the user has `notifications_enabled=False` or no linked Telegram chat is left `pending` rather than immediately failed or cancelled — the worker's next tick retries it for free once the user re-enables notifications or links Telegram, and if that never happens the existing 15-minute catch-up-window rule (spec §8.4) naturally cancels it later. No separate "undeliverable" status or handling was needed.
- 2026-09-18 — `telegram_blocked` is never used to *skip* a send attempt — the worker always calls the Telegram API regardless of the flag's current value, and sets it from the actual outcome (true on a blocked-bot error, cleared to false on any successful send). This makes the flag self-healing the moment the user unblocks the bot, instead of needing a separate "did they unblock yet" check.
- 2026-09-18 — The reminder's inline "Open" button (spec §8.3) links to `{PUBLIC_URL}/tasks/list/{list_id}`, not a deep link to the specific task — no route or mechanism exists anywhere in the app to open a specific task's detail dialog from a URL (every view manages that dialog's open/closed task id as local component state); the same list-level-only linking choice was already made for Stage 10's "Linked tasks" panel navigation for the identical reason.
- 2026-09-18 — After a recurring task's `occurrence` reminder is actually sent, the worker schedules the *next* occurrence's reminder immediately (spec §8.4: "после отправки ИЛИ выполнения/пропуска") — independent of the task's own `due_date`, which only advances when the user completes or skips it. The two paths can both fire for the same task (send schedules occurrence N+1's reminder; later completing occurrence N advances the task's due_date to N+1 too) without conflict, since `recompute_reminders_for_task`'s upsert-by-key logic treats a matching existing row as already correct.
- 2026-09-18 — Stage 12 bot quick add: spec §9's "вынести в общий модуль бэкенда, используемый и API quick add ... и ботом" is conditioned on "если разбор делается на сервере" (if parsing happens server-side) — Stage 8 already made web quick add parse client-side (chrono-node in `quickAddParser.ts`), so there's no server-side caller for the shared module to serve besides the bot. Built `app/services/quick_add.py` as a proper standalone backend module anyway (not inlined into `bot/handlers.py`), matching the spec's intent, even though only the bot calls it today.
- 2026-09-18 — The bot's date parsing (`dateparser`, English + Russian) doesn't expose which sub-phrase was a *time* the way chrono-node's `isCertain('hour')` does, so `app/services/quick_add.py` uses a regex heuristic (`\d{1,2}:\d{2}`, `\d{1,2}(am|pm)`, `noon`/`midnight`, `at \d`, `в \d{1,2}`) on the matched date substring to decide whether a time was actually specified. Covers the common English and Russian phrasings from the spec's own examples; an unusual time phrasing (e.g. spelled-out RU hour words with no digits) would be missed and fall back to date-only, matching quick add's own "leave dueTime null" behavior for an ambiguous match rather than guessing wrong.
- 2026-09-18 — Found while building the bot parser: a recurrence phrase combined with only a time and no explicit date (e.g. "every monday 9am") resolves `due_date` to *today* rather than null, because both chrono-node and dateparser default a bare time's date component to the reference date rather than leaving it unset — so `computeDefaultRecurrenceStartDate`/`default_recurrence_start_date`'s "pick the next matching weekday" fallback is never reached in this specific phrasing (it only fires when no date-ish substring matches at all). This is a pre-existing characteristic of the web quick add too (`quickAddParser.ts` has the same unconditional `dueDate = format(dt, ...)` whenever chrono returns any result), not something introduced here — mirrored as-is in the bot for consistency between the two entry points rather than fixed in only one. Worth revisiting both together if it proves confusing in practice.
- 2026-09-18 — The bot's "recurring task needs a time" follow-up (spec §9: "бот спрашивает время кнопками/сообщением") is tracked in an in-memory `dict[telegram_user_id, draft]` inside `bot/handlers.py`, not a database table — a bot process restart mid-conversation drops the pending draft, and the user just re-sends their original text. Accepted per the spec's own "не усложнять" rule 0.2 guidance: a `pending_quick_adds` table only to survive a restart mid-conversation is disproportionate to the problem.
- 2026-09-18 — The bot's "Change list"/"Undo" buttons (spec §9) reuse the same `tasks_service.update_task`/`delete_task` functions the web API calls, wrapped in a try/except for the `HTTPException` they raise on a cross-user or missing task (translated to a Telegram alert) — no separate bot-specific task-mutation path, and the same `get_owned_or_404` isolation guarantee applies without re-implementing it.
- 2026-09-18 — Stage 13 export/import: a note's `content` column already stores its frontmatter block verbatim (`sync_note_from_content` parses frontmatter into its own column but never strips it back out of `content` — see `app/services/note_links.py`), so vault export just writes `note.content` to the `.md` file byte-for-byte, and import passes a `.md` file's raw text straight into `create_note`/`sync_note_from_content` unmodified. - 2026-09-22 — The markdown-preview CSP fix (82caca2) was correct but never took effect for the user, exposing two more bugs in `deploy/nginx.conf.template`. First: `location /` had no `Cache-Control`, so browsers cache `index.html` on nginx's default heuristic (Last-Modified/ETag only) and can keep serving a stale document — with its stale CSP header — across a redeploy until a hard refresh; confirmed live by comparing a `fetch(..., {cache:'no-store'})` (got the new header) against a plain navigation in an already-open tab (still served the pre-fix header from disk cache). Added `add_header Cache-Control "no-cache" always;` to `location /` so every load revalidates (a cheap 304 via the existing ETag, not a full re-fetch). Second, caught while adding that: nginx's `add_header` doesn't merge across levels — a location block that declares even one `add_header` stops inheriting *all* of them from the server block. `location /assets/` (existing) and the newly-touched `location /` both declare their own `Cache-Control`, which was silently dropping the server-level CSP/X-Frame-Options/nosniff/Referrer-Policy for every document and asset response. Fixed by repeating the full header set in both locations rather than restructuring around `map`/`set` — more repetition, but the standard nginx idiom for this and easy to grep for the next time a location needs its own header.
